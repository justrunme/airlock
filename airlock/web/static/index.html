Why I built Airlock

Without Airlock

An AI agent follows a malicious instruction hidden in a log and attempts an unsafe action. Whatever it proposes runs with the agent's access to my host and keys.

With Airlock

The action is independently checked, blocked before execution, and recorded in a verifiable receipt. Safe work still runs, inside a sandbox with no network, and I get a report.

An AI agent can make a mistake. I built Airlock so that mistake does not automatically become my incident.

How a proposed action moves

BLOCKED the gate denied it before anything ran · ALLOWED it passed the gate · CONTAINED allowed code ran in the restricted sandbox (runsc, no network, limits) · TERMINATED the sandbox stopped it (killed_by=timeout or oom on this demo path) · VERIFIED the receipt's signature and receipt hash check out. A valid signature means the receipt was not tampered with; it does not by itself prove the world-state claim inside the receipt.

What I guarantee: every action the agent proposes is checked by the policy before anything runs, denied code never reaches a container, and every decision gets a signed, hash-chained receipt. You can check a receipt's signature and hash here in your browser or offline with the published key and tests/js/verify_cli.mjs from the repository; chain linkage is checked by the offline CLI (airlock verify-chain). What I do not: that the policy catches every attack, or that the host itself is honest. The receipt proves what was recorded, not that the machine was uncompromised. Known limitations.

SRE log triage live

This is the useful-result path for an SRE: the live model gets /work/input/app.log (on this corpus) and is asked to count ERROR/WARN lines, group errors, and write report.md that includes exactly one ```airlock-counts fence (ERROR: N / WARN: N only). Every proposal goes through the gate; allowed code runs in the sandbox. When it finishes you can download the report, read the raw stdout, see cleanup evidence, and an independent host recount against that fence (VERIFIED / FAILED / INCONCLUSIVE — prose and examples do not count). Receipts are labelled mode: live. Needs VULTR_INFERENCE_API_KEY. A run takes 20–90 seconds because the model reasons before answering. Claims are on this corpus only.

Attack arena

  
Submit Python or bash. It goes through the same policy and sandbox as the agent's code:
  no network, read-only root, no capabilities, no secrets, 10 s, 128 MB, 32 processes (RLIMIT_NPROC).
  Benign code runs; anything the policy does not understand is denied.

  
Runtime containment on this demo (owner scope):
  only timeout and memory. Each must pass the unchanged production gate,
  fail closed in the real sandbox (killed_by=timeout / killed_by=oom),
  then a healthy print(1+1) with exit 0, stdout 2, and cleanup.
  Structured result: PASS / FAILED / INCONCLUSIVE —
  do not treat anything but a live PASS as a filmable claim.
  Network isolation and read-only rootfs are not demonstrated on this path
  (no egress / write-outside runtime probes in the public demo; unit proofs in
  tests/test_sandbox.py are separate and must not be filmed as this Arena flow).

Verify a receipt in your browser

  
Verification runs here, with WebCrypto Ed25519 and SHA-256 and an RFC 8785 canonicaliser
  in verify.js (no dependencies). Nothing is sent to the server.
  Steps: strict JSON (duplicate keys rejected) → schema → SHA-256 of the canonical body
  → Ed25519 signature. Chain linkage is checked by the offline CLI
  (airlock verify-chain).

Known limitations

  

    
LimitationWhat it means

    
      
Containers share the host kernelUnder runc a kernel bug is a host escape. This deployment runs gVisor (runsc), which puts a user-space kernel in between and shrinks that surface. It does not remove it.

      
The static policy is incompleteIt is an allow-list parser for a subset of Python and bash. Unknown constructs are denied, but a bypass in what it does allow is possible. The sandbox is the second line.

      
Signatures cover the record, not the hostA valid signature proves the receipt came from the holder of this key and was not edited. It does not prove the host was honest or uncompromised when it wrote it.

      
No egress allow-listThe only network mode is none. Tasks that need the network cannot run here.

      
The control process can reach the Docker socketThe API service runs as an unprivileged user in the docker group, which is root-equivalent on this VM. The socket is never mounted into a sandbox or exposed over the network.

      
The signing key lives on this VMThe Ed25519 key sits on the same VM as the API process, and that process can reach Docker. Whoever controls the host can sign anything. The receipts prove integrity of the record, not honesty of the host.

      
Receipts are kept, not prunedDeleting one breaks the hash chain. Old work dirs and containers are pruned by a timer.
